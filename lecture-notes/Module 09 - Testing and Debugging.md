# Module 09: Testing and Debugging

## 1. Why automated tests

You've been testing your API since module 03, by hand, with `curl` and the browsable API. That works, right up until it doesn't. Manual testing checks whatever you remembered to check, on the day you remembered to check it, and its results live in your head rather than in your repository.

An **automated test** is code that runs your code and asserts something about the result. Its real value isn't proving that a feature works today, which you already know because you just built it. Its value is telling you, three sprints later, that something you changed for an unrelated reason quietly broke it.

The Project requires automated tests demonstrating that the API functionality you add or modify behaves as intended, including successful requests, validation, and error responses. That last pair matters: a test suite that only ever checks the happy path is the automated equivalent of the acceptance criteria problem from module 08.

| Test type   | What it checks                                | Where you'll write it       |
| ----------- | --------------------------------------------- | --------------------------- |
| Unit        | One function or method in isolation           | Model methods, helpers      |
| Integration | Several parts working together                | An API endpoint, end to end |
| Component   | A UI component renders and responds correctly | React Native components     |

## 2. Testing the Django API

Django includes a test runner, and DRF adds a test client that speaks HTTP. No extra installation is needed.

Every app already has a `tests.py` file, generated by `startapp` back in module 02. Replace the contents of `studios/tests.py`.

```python
from django.contrib.auth.models import User
from rest_framework import status
from rest_framework.test import APITestCase
from .models import Studio


class StudioListTests(APITestCase):
    def setUp(self):
        self.user = User.objects.create_user(
            username="testuser",
            password="testpassword123",
        )
        self.studio = Studio.objects.create(
            owner=self.user,
            name="CityFit",
            suburb="Dunedin Central",
            city="Dunedin",
        )

    def test_anyone_can_list_studios(self):
        response = self.client.get("/api/studios/")

        self.assertEqual(response.status_code, status.HTTP_200_OK)
        self.assertEqual(len(response.data), 1)

    def test_anonymous_user_cannot_create_studio(self):
        response = self.client.post("/api/studios/", {
            "name": "Harbourside Yoga",
            "suburb": "St Kilda",
            "city": "Dunedin",
        })

        self.assertEqual(response.status_code, status.HTTP_401_UNAUTHORIZED)
        self.assertEqual(Studio.objects.count(), 1)
```

Run them.

```bash
python manage.py test
```

A few things are happening that are worth understanding rather than copying.

`setUp` runs before **every** test method, not once for the class. Each test therefore starts from an identical, freshly built world. That's deliberate: tests that share state pass or fail depending on the order they happen to run in, which makes a failure almost impossible to interpret.

Django creates a **separate test database**, runs your migrations into it, and destroys it afterwards. Your development data is never touched, and the tests never depend on whatever you happened to type into the admin panel last week.

`self.client` is DRF's test client. It makes real requests through your real URL routing, views, serializers, and permissions. That makes these integration tests rather than unit tests: they're checking the whole stack you built in modules 03 and 07 behaves correctly together.

Notice the second test asserts two things: the status code, _and_ that no studio was actually created. Why isn't the status code enough on its own? _Answer: because a 401 tells you what the API said, not what it did. A bug that rejects the request and creates the row anyway would pass a status-code-only assertion. Asserting the state as well as the response is what makes the test meaningful._

### 2.1 Arrange, Act, Assert

Every test above follows the same three-part shape, and naming it makes it easier to write the next one.

**Arrange** the world into the state the test needs. **Act**, performing the single thing being tested. **Assert** that what you expected actually happened.

```python
def test_studio_requires_a_name(self):
    # Arrange
    self.client.force_authenticate(user=self.user)

    # Act
    response = self.client.post("/api/studios/", {
        "suburb": "St Kilda",
        "city": "Dunedin",
    })

    # Assert
    self.assertEqual(response.status_code, status.HTTP_400_BAD_REQUEST)
    self.assertIn("name", response.data)
```

`force_authenticate` logs a user in for the test without going through the token endpoint, which keeps the test focused on the thing it's actually about. This test is about validation, not about JWTs; if it obtained a real token first, a broken token endpoint would fail it, and the failure message would point you at entirely the wrong file.

If a test has two Acts, it's two tests. A method called `test_creating_and_updating_and_deleting_a_studio` tells you nothing useful when it fails, because "it broke" doesn't say which of the three broke.

### 2.2 Testing permissions

Module 07's `IsOwnerOrReadOnly` is exactly the kind of rule that deserves a test, because it's invisible: nothing on screen shows you it's working, and it only fails for a user who isn't you.

```python
def test_user_cannot_edit_another_users_studio(self):
    other_user = User.objects.create_user(
        username="otheruser",
        password="otherpassword123",
    )
    self.client.force_authenticate(user=other_user)

    response = self.client.patch(
        f"/api/studios/{self.studio.id}/",
        {"name": "Hijacked"},
    )

    self.studio.refresh_from_db()
    self.assertEqual(response.status_code, status.HTTP_403_FORBIDDEN)
    self.assertEqual(self.studio.name, "CityFit")
```

`refresh_from_db()` reloads the object from the database, because `self.studio` is a Python object still holding whatever values it had in `setUp`. Without that line you'd be asserting against a stale copy in memory and the test would pass even if the database row had been changed.

| Key terms            |                                                                           |
| -------------------- | ------------------------------------------------------------------------- |
| `APITestCase`        | DRF's test case class, providing an HTTP-speaking `self.client`           |
| `setUp`              | Runs before every test method, building a fresh starting state            |
| `force_authenticate` | Authenticates the test client without going through a real login          |
| `refresh_from_db`    | Reloads a model instance from the database, discarding the in-memory copy |
| Arrange, Act, Assert | The three-part shape of a readable test                                   |

## 3. Test coverage, and what it doesn't tell you

**Coverage** measures how much of your code was executed while your tests ran.

```bash
pip install coverage
coverage run --source="." manage.py test
coverage report
```

This is genuinely useful for finding code no test touches at all, which is usually where the surprises are hiding. It's much less useful as a target. Code can be executed by a test without anything meaningful being asserted about it, so 100% coverage is entirely achievable with tests that would pass even if the code were wrong.

Treat a coverage report as a map of where you haven't looked, not as a score.

## 4. Testing React Native components

The client side needs a separate toolchain. Install it in your Expo project.

```bash
npx expo install jest jest-expo @testing-library/react-native --dev
```

Add the following to `package.json`.

```json
{
  "scripts": {
    "test": "jest"
  },
  "jest": {
    "preset": "jest-expo"
  }
}
```

Create `components/StudioRow.test.tsx`, testing the component from modules 05 and 06.

```tsx
import { render, screen, fireEvent } from "@testing-library/react-native";
import { StudioRow } from "./StudioRow";

describe("StudioRow", () => {
  it("displays the studio name and location", () => {
    render(
      <StudioRow
        name="CityFit"
        suburb="Dunedin Central"
        city="Dunedin"
        isFavourite={false}
        onToggleFavourite={() => {}}
      />,
    );

    expect(screen.getByText("CityFit")).toBeTruthy();
    expect(screen.getByText("Dunedin Central, Dunedin")).toBeTruthy();
  });

  it("calls onToggleFavourite when the heart is pressed", () => {
    const onToggleFavourite = jest.fn();

    render(
      <StudioRow
        name="CityFit"
        suburb="Dunedin Central"
        city="Dunedin"
        isFavourite={false}
        onToggleFavourite={onToggleFavourite}
      />,
    );

    fireEvent.press(screen.getByText("♡"));

    expect(onToggleFavourite).toHaveBeenCalledTimes(1);
  });
});
```

```bash
npm test
```

`jest.fn()` creates a **mock function**: a stand-in that records how it was called, without doing anything. That's the whole trick for testing a component like `StudioRow`. Module 05 made a point of `StudioRow` not knowing anything about favourites, only calling whatever function it was handed, and that design is exactly what makes it testable in isolation now. A component that managed its own favourites list internally would need its internals inspected to test the same behaviour.

Notice what these tests query by: visible text, the way a user would find it, rather than by internal component structure. A test written against the rendered output survives a refactor of the component's internals. A test written against its internals fails every time you reorganise them, without anything having actually broken.

| Key terms   |                                                         |
| ----------- | ------------------------------------------------------- |
| Jest        | The test runner used for JavaScript and TypeScript      |
| `render`    | Renders a component into a test environment             |
| `screen`    | Queries the rendered output the way a user would see it |
| `fireEvent` | Simulates a user interaction such as a press            |
| `jest.fn()` | A mock function that records how it was called          |

## 5. Mocking the network

A component that fetches data presents a problem: you don't want your test suite depending on a Django server being running, and you certainly don't want tests creating rows in a real database.

**Mocking** replaces a real dependency with a controlled fake.

```tsx
import { render, screen, waitFor } from "@testing-library/react-native";
import StudiosScreen from "../app/index";
import * as studiosApi from "../studiosApi";

jest.mock("../studiosApi");

describe("StudiosScreen", () => {
  it("shows studios once they have loaded", async () => {
    jest
      .spyOn(studiosApi, "getStudios")
      .mockResolvedValue([
        { id: 1, name: "CityFit", suburb: "Dunedin Central", city: "Dunedin" },
      ]);

    render(<StudiosScreen />);

    await waitFor(() => {
      expect(screen.getByText("CityFit")).toBeTruthy();
    });
  });

  it("shows an error message when the request fails", async () => {
    jest
      .spyOn(studiosApi, "getStudios")
      .mockRejectedValue(new Error("Network request failed"));

    render(<StudiosScreen />);

    await waitFor(() => {
      expect(screen.getByText(/could not load/i)).toBeTruthy();
    });
  });
});
```

`waitFor` retries its assertion until it passes or times out, which is necessary because the fetch resolves asynchronously and the screen isn't showing studios at the instant it renders.

The second test is the more valuable of the two. Module 06's Task 5 asked you to add an error state and test it by stopping your Django server by hand. This is that same test, except it runs in half a second, every time, without you remembering to do anything. Failure states are the hardest thing to trigger manually and the easiest thing to mock, which is exactly why they're so often untested.

This is also the payoff for module 07's `apiFetch` wrapper. Because every request goes through one module, one mock covers the whole app's network layer. Screens that called `fetch` directly would each need mocking separately.

## 6. Debugging

Tests tell you _that_ something is wrong. Debugging is working out _why_.

### 6.1 Beyond print statements

`print()` and `console.log()` are legitimate tools, and there's no shame in reaching for them. But both languages have something better for anything more than a one-line check.

In Python, `breakpoint()` pauses execution and drops you into an interactive prompt, with every variable in scope available to inspect and query.

```python
def perform_create(self, serializer):
    breakpoint()
    serializer.save(owner=self.request.user)
```

Run the server, make the request, and your terminal becomes a debugger. Type a variable name to see it, `n` to step to the next line, `c` to continue, `q` to quit. The advantage over `print` is that you don't have to have guessed in advance which variable would be the interesting one.

In React Native, pressing `j` in the terminal running `npx expo start` opens the JavaScript debugger, where you can set breakpoints in your editor and step through component code with the full call stack visible.

### 6.2 Reading a traceback

A Python traceback reads bottom-up in importance: the last line names the actual error, and the frames above show the path that reached it. The frame you care about is usually the last one pointing at a file you wrote, rather than one inside `site-packages`.

```
  File "/.../studios/views.py", line 18, in perform_create
    serializer.save(owner=self.request.user)
AttributeError: 'AnonymousUser' object has no attribute 'id'
```

That error says something precise: `request.user` is `AnonymousUser`, meaning no authentication happened. The bug isn't in `perform_create` at all; it's a missing or wrong permission class, or a token that never arrived. Reading the message literally, rather than pattern-matching it to the last similar error you saw, is most of the skill.

### 6.3 Narrowing down

When something fails and you have no idea why, the most reliable technique isn't cleverness, it's halving. Confirm whether the API returns correct data with `curl`. If it does, the bug is in the client. If it doesn't, the bug is in the server, and you've eliminated half your codebase with one command.

Then halve again inside whichever half is guilty. Four or five halvings will locate almost any bug in a project this size, and it works even when you have no hypothesis at all, which is precisely when you need it most.

Before starting a debugging session, write down the one sentence describing what you expected to happen and what actually happened instead. It sounds trivial. It regularly ends the session on its own, because stating the expectation precisely often reveals that the expectation was the wrong thing.

| Key terms      |                                                                     |
| -------------- | ------------------------------------------------------------------- |
| `breakpoint()` | Pauses Python execution and opens an interactive debugger           |
| Traceback      | The stack of calls that led to an error, with the error itself last |
| Mocking        | Replacing a real dependency with a controlled fake                  |
| `waitFor`      | Retries an assertion until it passes, for asynchronous behaviour    |
